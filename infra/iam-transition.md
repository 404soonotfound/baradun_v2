# CDK 실행 정책 및 관리자 전환 (GH-300)

기준은 결정 기록 21장과 25장입니다. 스택 배포, 계정 권한 변경, 비용 제어 변경은 별도 승인 후 진행합니다.

## 정책을 적용하기 전 확인

1. 진행 중인 인프라 실행이 끝났는지 확인합니다. CloudFormation에서 `BaradunV2`와 `CDKToolkit` 상태 및 현재 사용 중인 실행 역할을 확인합니다. #418의 다음 main 배포와 겹치지 않는 작업 시간을 정합니다.
2. `iam get-policy`, `iam get-policy-version`, `iam list-attached-role-policies`, `iam list-role-policies`로 기존 기본 버전과 연결 상태를 확인합니다. 정책 이름과 기존 버전 ID를 기록하고 이전 정상 버전을 보관합니다. 정책 문서는 제한된 로컬 파일에 저장합니다.
3. `cloudformation get-template --template-stage Original`로 읽은 운영 템플릿을 합성 결과와 비교합니다. 로컬에서는 `cdk synth --no-lookups`를 사용합니다. 읽기 전용 비교에서는 변경 세트를 만들지 않습니다. 템플릿이 같아도 리소스 생성·변경·삭제 권한이 실증된 것은 아닙니다.
4. 후보 문서는 IAM Policy Simulator의 Custom 모드에서 검증합니다. 각 동작의 리소스와 필요한 조건 값을 넣고 허용 사례와 거부 사례를 각각 확인합니다. IAM Access Analyzer의 기본 정책 유효성 검사도 사용할 수 있습니다. 유료 분석기나 유료 사용자 지정 검사는 이 작업에서 만들거나 실행하지 않습니다. [IAM Policy Simulator](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_testing-policies.html) · [Access Analyzer 요금](https://aws.amazon.com/iam/access-analyzer/pricing/)
5. 현재 서비스 스택의 CloudFront 프로젝트 태그와 배포 대상 ARN이 후보 정책의 조건을 만족하는지 확인합니다. 조건을 충족하지 않으면 현재 정책을 유지하고 별도 태그 반영 계획을 준비합니다. [기존 태그 전환 절차](README.md#정책-적용과-되돌리기-절차)

## 관리자 접근 전환

이 계정은 2026-11-13에 AWS Organizations를 구성하면서 Paid 플랜으로 전환했습니다. 기존 **IAM Identity Center 조직 인스턴스**의 AWS 계정 접근을 우선 사용합니다. Identity Center 자체에는 추가 요금이 없으며, Paid 플랜의 실제 사용량 청구와 D25의 월 US$1 미만 운영 기준은 계속 적용합니다. MFA 필수 임시 IAM 관리자 역할은 기존 Identity Center 경로를 쓸 수 없을 때의 대안입니다. [계정 플랜 이력](README.md#비용-방어-범위) · [Identity Center 요금](https://aws.amazon.com/iam/identity-center/faqs/)

1. 기존 IAM 사용자 정책·그룹·경계와 장기 키를 쓰는 자동화를 목록화합니다. 독립 비상 접근과 계정 복구 정보에 접근 가능한지 확인합니다.
2. 기존 조직 인스턴스에서 이 AWS 계정에 대한 할당, MFA 설정, 권한 세트를 확인합니다. 일상 조회·배포와 관리자 작업의 권한을 구분하고, 관리자 권한 세트의 최대 세션은 1시간으로 둡니다. 할당이나 정책을 바꿔야 하면 별도 승인을 받습니다.
3. 기존 관리자 세션을 유지한 채 별도 브라우저에서 AWS 액세스 포털을 확인합니다. CLI에서는 `aws sso login --profile baradun-sso` 후 `aws sts get-caller-identity --profile baradun-sso`로 대상 계정과 역할을 확인합니다. 읽기 전용 검증으로 스택·정책 접근을 확인하고, 독립 비상 접근도 별도로 점검합니다.
4. 검증 후 별도 승인으로 상시 관리자 정책을 분리합니다. 기존 자동화는 단기 세션 또는 OIDC 경로를 사용하며, 장기 키는 의존성을 확인한 뒤 정리합니다. 실패하면 독립 비상 접근으로 직전 정책 연결을 복원합니다. [IAM 임시 역할 대안](README.md#mfa-조건-임시-관리자-역할-전환-절차)

비상용 접근은 일상 세션과 별도로 보관합니다. 계정 복구 연락처와 MFA 복구 경로를 점검하고 복구 수단을 접근 통제된 오프라인 또는 별도 보관소에 둡니다. 복구 코드, 키, 비밀번호는 이 저장소와 작업 로그에 남기지 않습니다.

- [ ] 기존 관리자, Identity Center 권한 세트, 독립 복구 수단의 접근 확인
- [ ] 별도 세션에서 MFA와 관리자 권한 세트의 세션 제한 확인
- [ ] 대상 계정·리전·역할 및 기존 정책 기본 버전 확인
- [ ] CI·로컬 배포의 사용 주체와 다른 자동화 의존성 확인
- [ ] 정책 전환과 관리자 권한 분리에 각각 승인 확보

## 실환경 적용과 복구

| 순서          | 실행 후 확인                                                                                             | 실패 시                                                                                                  |
| ------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 권한 경계     | `iam get-policy`, `iam get-policy-version`, `iam get-role`로 기본 버전과 스택 역할 연결 확인             | 이전 기본 버전 복구 후 중단                                                                              |
| CDK 실행 정책 | `iam get-policy-version`, `iam list-attached-role-policies`로 후보 문서와 연결 확인                      | 직전 정상 실행 정책을 먼저 복구하고 필요한 경우 경계를 복구                                              |
| 스택 확인     | `cloudformation describe-stacks`, `get-template`, `describe-stack-events`로 상태·템플릿·실패 이벤트 확인 | 정책 복구 뒤 스택 롤백을 확인. 롤백 자체가 권한 문제로 멈췄다면 권한 복구 뒤 승인된 세션에서 이어서 실행 |

정책 문서 갱신은 기존 README의 관리형 정책 버전 절차를 사용합니다. 이전 정상 버전과 부트스트랩 파라미터를 보존합니다. 변경 없는 템플릿 비교 결과는 핸들러 권한의 실증으로 기록하지 않습니다. 실환경 핸들러 확인은 별도 승인된 작업에서 수행합니다.

## 일상 배포와 CDKToolkit 초기 설정

| 경로                            | 권한과 확인 근거                                                                                                                                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| #418 GitHub 인프라 배포         | OIDC 역할이 CDK의 배포·파일 게시·조회 역할을 맡음. CI 자체 정책은 스택·정책·함수 상태와 로그 조회에 한정됨. 승인 환경과 현재 보호 규칙을 유지함.                                                       |
| 로컬 `deploy:infra`             | CDK의 같은 서비스 스택 배포 경로 사용. 관리자 프로필은 스택 밖 정책을 조회하며, 승인된 경우에만 기존 절차로 경계를 갱신함.                                                                             |
| CloudFormation 서비스 실행 역할 | `cfn-execution-policy.json`과 `cfn-execution-workload-policy.json`을 함께 사용함. 합성된 서비스 리소스의 생성·조회·변경·삭제·태그 권한을 기존 고정 AWS 참조 검사로 대조함.                             |
| CDKToolkit 초기 설정            | `bootstrap/cdk-toolkit-setup-policy.json`은 현재 표준 qualifier, 서울 리전, 기본 자산 이름 및 기존 부트스트랩 옵션 기준 후보임. 관리자 승인 후 일시적으로 사용하는 별도 설정 역할의 권한으로만 검토함. |

초기 정책 후보 `BaradunCdkToolkitSetup`은 CDKToolkit 변경 세트, 자산 버킷·저장소, CDK 역할, 부트스트랩 버전 파라미터에 한정합니다. 이 정책은 CloudFormation 서비스 실행 정책 목록과 GitHub OIDC 역할에 추가하지 않습니다. `deploy.mjs`의 비교 결과는 안내용입니다. 미설치나 조회 불가 상태에서도 일상 배포의 기존 판정은 유지합니다.

### 초기 설정 역할 점검표

- [ ] 설정 역할은 관리자에 준해 관리합니다. 승인된 사람만 MFA를 거쳐 맡고, 세션은 최대 1시간으로 제한합니다. 호출 전에 `aws sts get-caller-identity --profile "$setup_profile"`로 대상 계정과 역할을 확인합니다.
- [ ] `aws cloudformation describe-stacks --stack-name CDKToolkit`으로 variant·qualifier·신뢰 계정·자산 설정을 확인합니다. 다른 옵션, 고객 관리 KMS 키, 별도 권한 경계를 쓰는 환경은 그 구성에 맞는 정책을 따로 검토합니다.
- [ ] 초기 설정 후 CDKToolkit 상태, 실행 역할에 연결된 두 정책, 자산, 버전 파라미터를 확인합니다. 배포·파일 게시·이미지 게시·조회·CloudFormation 실행 역할 **5개 모두**에 대해 `iam get-role`의 `AssumeRolePolicyDocument`와 `iam list-role-policies`·`iam get-role-policy`의 인라인 정책을 비교합니다. 사용한 CDK 버전의 `cdk bootstrap --show-template`에 실제로 승인한 부트스트랩 파라미터를 대입한 결과가 기준입니다. 다르면 다음 배포로 넘어가기 전에 차이를 확인합니다.
- [ ] 설정이 끝나면 별도 승인된 관리자 세션에서 초기 정책을 분리하거나 전용 설정 역할을 삭제합니다. 정책을 분리했으면 `list-attached-role-policies`에서 해당 정책이 없는지 확인합니다. 역할을 삭제했으면 `get-role`에서 `NoSuchEntity`인지 확인합니다. 조회 권한 오류는 삭제 확인으로 보지 않습니다.

정책을 분리하고 확인할 때는 전용 설정 역할 세션을 종료한 뒤 별도 관리자 프로필을 사용합니다. 아래 변수에는 승인된 역할 이름과 초기 설정 정책 ARN을 넣습니다.

```bash
aws iam detach-role-policy --role-name "$setup_role" --policy-arn "$setup_policy_arn"
aws iam list-attached-role-policies --role-name "$setup_role" \
  --query "AttachedPolicies[?PolicyArn=='$setup_policy_arn'].PolicyArn"
```

| 검증 항목      | 확인 범위                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 스택 템플릿    | 운영 원본과 합성본을 구조 비교. AWS 조회에서 물음표로 반환된 비ASCII 문자와 CDK 빌드 메타데이터를 제외한 비교임.                                                                                                   |
| 일상 실행 정책 | 공식 IAM 참조와 합성 리소스의 필수 핸들러, 역할 경계 적용, 제한된 예외를 테스트함. 실환경 정책에서 서비스 단위 와일드카드를 명시 동작으로 대체하는 효과는 정책 문서 기준임.                                        |
| 초기 설정 정책 | 공식 참조에서 동작 이름과 리소스 종류를 대조함. 권한 시뮬레이션은 표본이며 CDKToolkit 최초 생성 및 롤백의 전체 실행은 **[확인]**으로 남김.                                                                         |
| 권한 경계      | 스택이 만드는 런타임 역할의 상한과 CloudFormation의 실행 정책은 적용 주체가 다름. 런타임 동작을 실행 역할에 추가하지 않음. 스택 역할에 경계가 붙는지, 초기 설정 권한이 경계 및 일상 역할에 들어가지 않는지 검사함. |
| 배포 호환      | GitHub OIDC·로컬 CDK 역할·스택 런타임 경계의 권한 문서는 유지함. 시뮬레이션은 서비스 Lambda 생성·갱신·삭제 허용, 일상 역할의 Toolkit 변경 및 경계 편집 거부, 초기 역할의 서비스 Lambda 갱신 거부를 확인함.         |

서비스 스택 정책에서 범위 제한이 불가능하거나 서비스 조회에 필요한 일부 권한은 공식 참조와 런타임 제약에 따라 유지합니다. 생성이 필요한 리소스, 전역 리소스의 서비스 특성, 그리고 계정·리전 단위 조회가 해당합니다. 현재 CloudFront 배포 두 개의 프로젝트 태그 존재를 읽기 전용으로 확인했습니다. 그 외 실제 Create·Update·Delete와 롤백은 적용 승인 이후 확인합니다.
