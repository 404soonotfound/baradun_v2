# 기술 문서 작성 규칙

이 저장소에서 문서를 쓰거나 고칠 때 따르는 규칙입니다. 사람과 에이전트 모두 이 규칙을 따릅니다. 이 규칙을 따르면 처음 보는 사람도 문서만 읽고 목적을 이룰 수 있고 같은 내용이 문서마다 다르게 적히는 일을 막을 수 있습니다.

토스 [테크니컬 라이팅 가이드](https://github.com/toss/technical-writing)(CC BY-NC-SA 4.0)의 원칙을 이 저장소에 맞게 요약하고 고쳐 썼습니다. 원문을 옮기지 않았으므로 예시와 자세한 설명은 원문을 봅니다.

## 적용 범위

| 대상                                          | 이 규칙       | 따로 따르는 규칙                                                              |
| --------------------------------------------- | ------------- | ----------------------------------------------------------------------------- |
| 루트 `README.md`, 폴더별 `README.md`, `docs/` | 전부          | —                                                                             |
| PR 설명·이슈 본문·리뷰 답글                   | 3·4·5장       | 형식은 [AGENTS.md](../AGENTS.md) '브랜치·커밋·PR'                             |
| `AGENTS.md` 같은 에이전트 지침                | 3·4·5장       | 문체는 지금 문서를 따름(명령형 '~한다')                                       |
| 화면 문구                                     | 적용하지 않음 | 문구 키와 제품 규칙([AGENTS.md](../AGENTS.md) '제품 규칙', 각 앱 `AGENTS.md`) |
| 코드 주석                                     | 적용하지 않음 | 명사형 종결(~함, ~음)                                                         |

## 1. 문서 유형

독자가 원하는 것에 따라 문서 유형이 정해지고 유형마다 갖출 내용이 다릅니다. 한 문서에 여러 유형을 섞지 않습니다. 섞어야 하면 절을 나누고 긴 내용은 다른 문서로 옮겨 링크합니다.

| 유형      | 독자가 원하는 것              | 이 저장소 예                            | 갖출 것                                                 |
| --------- | ----------------------------- | --------------------------------------- | ------------------------------------------------------- |
| 학습      | 처음부터 따라 해 보기         | 루트 README '빠르게 실행하기'           | 목표, 준비물, 단계별 명령, 결과 확인                    |
| 문제 해결 | 정해진 작업 끝내기, 장애 대응 | `infra/README.md`의 점검 켜기, 되돌리기 | 목표나 증상, 원인·배경, 절차(명령), 확인 방법, 되돌리기 |
| 참조      | 정확한 값과 규칙 찾기         | `data/beaches/README.md`, 계약 스키마   | 빠짐없는 항목, 같은 꼴의 표, 예시                       |
| 설명      | 왜 그렇게 했는지 이해하기     | ADR, 루트 README '설계 결정'            | 배경과 문제, 고른 방법, 버린 대안과 이유, 결과          |

## 2. 정보 구조

- **개요를 맨 앞에 둡니다.** 첫 단락에 무엇을 다루는지, 누가 읽는지, 읽고 나면 무엇을 할 수 있는지 씁니다.
- **가치를 먼저 씁니다.** 배경 설명보다 결론, 명령, 독자가 얻는 것을 먼저 쓰고 세부 사항은 뒤에 둡니다.
- **한 문서는 한 목표만 다룹니다.** 제목이 `####`(H4)까지 내려가면 문서를 나눌지 검토합니다. 루트 README에는 운영 절차를 넣지 않고 해당 폴더 README로 링크합니다.
- **구조를 예측할 수 있게 합니다.** 같은 수준의 제목은 같은 꼴(명사형이나 동사형 중 하나)로 씁니다. 같은 종류의 절은 같은 순서로 배치합니다.
- **제목은 짧은 평서문으로 씁니다.** 핵심 키워드를 넣고 30자 안팎으로 씁니다. 질문형이나 감탄형은 쓰지 않습니다.
- **새 개념은 처음 나올 때 설명합니다.** 링크만 걸어 두고 넘어가지 않습니다.

## 3. 문장

- **한 문장에는 생각 하나만 담습니다.** 길어지면 문장을 나눕니다.
- **말에 대한 말을 지웁니다.** '앞서 설명했듯이', '참고로 말씀드리면', '~에 대해 알아보겠습니다' 같은 표현은 쓰지 않습니다.
- **구체적으로 씁니다.**
  - 명사를 나열하지 말고 동사로 씁니다. '배포 진행 및 확인 수행'은 '배포하고 결과를 확인합니다'로 고칩니다.
  - 누가, 무엇을, 어디서, 어떻게 하는지 씁니다.
  - 수치와 기준을 씁니다. '자주 수집'이 아니라 '매시 3·18·33·48분'처럼 씁니다.
  - '빠르게', '최적화', '적절히' 대신 결과를 씁니다.
- **주체를 분명히 합니다.** 능동형으로 씁니다. 사람이 할 일은 사람을 주어로 쓰고 시스템 동작은 실제로 그 일을 하는 부품의 이름을 주어로 씁니다(예: '게시 함수가 manifest를 바꿉니다'). 사람이 할 일을 '~가 수행됩니다'처럼 숨기지 않습니다.
- **용어를 일관되게 씁니다.** 같은 개념은 4장의 이름 하나로만 부릅니다. 제품 이름은 공식 표기를 따릅니다(Next.js, CloudFront, DynamoDB).
- **약어와 내부 번호는 처음 나올 때 풀어 씁니다.** 'G1', 'B3', 'D20-1', 'BRD-118' 같은 번호만으로 뜻이 전해지게 쓰지 않습니다. 본문에서 뜻을 쓰고 번호는 근거로 괄호 안에 남깁니다.
- **자연스러운 한국어로 씁니다.**
  - 불필요한 한자어를 줄입니다: '수행하다', '진행하다', '~에 대하여', '~을 통해'.
  - 번역체를 고칩니다: '~를 가지다', '~하는 것이 가능하다', 행위 주체를 숨기는 '~에 의해' 피동문.
- **문서 하나 안에서는 문체를 하나만 씁니다.** 합니다체와 해요체 중 하나를 고르고 이미 있는 문서를 고칠 때는 그 문서의 문체를 따릅니다. 에이전트 지침(`AGENTS.md`)은 예외로 명령형 '~한다'를 씁니다.
- **문체 검사를 통과합니다.** 바뀐 `*.md` 줄과 커밋 메시지는 `tools/copy-lint`가 번역투·AI 문체 규칙으로 검사합니다(로컬 훅 `git config core.hooksPath .githooks`, PR은 CI `copy-lint`). 연결어미 뒤 쉼표(`~하고,`)처럼 이 문서에 없는 규칙도 있으니 걸린 곳은 고쳐서 다시 커밋합니다.

## 4. 이 저장소의 용어

| 쓰는 말                           | 뜻                                                       | 쓰지 않는 말           |
| --------------------------------- | -------------------------------------------------------- | ---------------------- |
| `특보 없음`·`이용불가`·`판단불가` | 화면 분류 세 가지. 이 표기 그대로 씀                     | 안전, 정상, 양호, 위험 |
| 관측 지연                         | 파고 측정이 90분을 넘김(판단불가 사유)                   | 데이터 오류, 결측 처리 |
| 가까운 관측 없음                  | 쓸 수 있는 측정소가 없음(분류에 영향 없음)               | 0, 정상                |
| 수집기                            | 외부 API를 부르는 Lambda(`services/src/collectors`)      | 크롤러                 |
| 게시 함수, 게시본                 | `publish-snapshot`과 그 함수가 올린 버전(`data/{버전}/`) | 배치, 스냅샷 서버      |
| 사용자 사이트, 운영자 사이트      | `apps/web`, `apps/admin`                                 | 프론트, 어드민 페이지  |
| 운영 API                          | `/ops/*`                                                 | 백오피스 API           |

- 활동 적합도, 추천, 점수, 레벨처럼 서비스가 판단하지 않는 개념을 기능처럼 쓰지 않습니다. 하지 않는 일을 밝힐 때만 씁니다.
- 내부 기획 용어(적합도, 필수 관측, 유효, 앞 판단 우선)는 외부 독자가 읽는 문서에 쓰지 않습니다.
- '안전해요', '추천'처럼 안전을 보장하는 표현은 문서에도 쓰지 않습니다.
- 시각은 KST인지 UTC인지 함께 씁니다.

## 5. 사실과 근거

- **확인한 사실만 씁니다.** 코드·설정·실행 결과로 확인한 내용만 쓰고 근거가 되는 파일 경로를 링크합니다.
- **측정하지 않은 수치는 쓰지 않습니다.** 추정치는 추정이라고 밝히고 근거를 함께 씁니다. 예: '월 약 US$0.4~0.9(결정 기록 D25-3 추정, 실제 청구액 미확인)'.
- **수치에는 단위·출처·기준 시각을 붙입니다.**
- **한 일과 할 일을 구분합니다.** 아직 하지 않은 일은 '예정'이나 '아직 없음'으로 씁니다. 지난 상태를 현재형으로 남겨 두지 않습니다.
- **코드와 문서를 함께 고칩니다.** 동작을 바꾼 PR에서 그 동작을 설명하는 문서도 같이 고칩니다.
- **기준 문서는 Notion입니다.** 저장소 문서와 Notion이 다르면 Notion을 따르고 차이를 보고합니다.
- **비밀값, 계정 번호, 개인 정보, 운영 데이터를 쓰지 않습니다.** 예시가 필요하면 `<PublisherFunctionName>`처럼 자리 표시를 씁니다.

## 6. 점검표

문서를 올리기 전에 확인합니다. 리뷰할 때도 이 항목으로 지적합니다.

- [ ] 첫 단락만 읽어도 무엇을 다루는지, 누가 읽는지 알 수 있다
- [ ] 문서 유형이 하나이고 그 유형이 갖출 것을 갖췄다
- [ ] 제목이 같은 꼴이고 30자 안팎이며 H4까지 내려간 곳은 나눌지 검토했다
- [ ] 한 문장에 생각이 하나이고 말에 대한 말이 없다
- [ ] 내부 번호와 약어를 처음 나올 때 풀어 썼다
- [ ] 4장 용어를 지켰고 같은 개념을 여러 이름으로 부르지 않았다
- [ ] 수치에 단위·출처·기준 시각이 있고 측정하지 않은 값이 없다
- [ ] 명령과 경로가 지금 코드와 맞다(실행하거나 파일을 열어 확인함)
- [ ] 비밀값, 계정 번호, 개인 정보가 없다
- [ ] `tools/copy-lint` 문체 검사를 통과했다
